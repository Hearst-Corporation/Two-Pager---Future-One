# A9 — RLS / IDOR audit — 2026-05-16

> Sprint context: 10-agent parallel review of the Prese Hub admin API.
> Scope: every `app/api/admin/**/route.js` plus `app/api/track/deck-view/route.js`.
> Method: static read of route handlers and SQL schemas — no runtime probing.

---

## 1. Executive summary

| Metric | Count |
|---|---:|
| Mutating routes audited | **24** (POST / PATCH / DELETE handlers) |
| Total route files audited | **35** |
| Routes that already enforce per-user ownership | **3** (comments PATCH/DELETE, notifications PATCH, team/[id]) |
| Routes safe-by-design under the shared-workspace model | **20** |
| Routes with a real exploitability concern (IDOR or design gap) | **1** (`POST /api/admin/team`, partial — see § 4) |
| **Truly broken IDOR risks** | **0** |

**Bottom line.** The codebase is currently a **single-tenant shared workspace** — every authenticated `editor` is expected to be able to read and mutate every operator, partner, initiative, task, hearst_* row. There is no `owner_id`, `tenant_id`, or `team_id` on any of the business tables. Classic cross-user IDOR therefore does not exist *yet*, but the moment a second tenant or per-user partition is introduced this codebase will be wide open — none of the routes scope queries by user. The 3 places where per-user ownership *does* exist (comments, notifications, profile self-edit) all check it correctly.

The provided helper `lib/auth-guards.js` is **not yet wired** anywhere. Wiring is a deliberate follow-up: every shared-workspace route should adopt `requireRowOwnership({ ..., allowSharedWorkspace: true })` so it at least asserts row existence before mutating, and so the day the data model gains an `owner_id` the upgrade is a one-line change per route.

| `crm.notifications` | `recipient_id` — correctly enforced in GET/PATCH |

The hearst_projects table is auto-created by `GET /api/admin/hearst/project` when no row exists, and the codebase always picks `.limit(1).single()` for the single project — strong evidence the app is meant to run as ONE deal in ONE workspace.

**Implication for IDOR.** With no per-user partitioning, "user A mutates user B's row" is by design — both users are intended to see the same row. The risks that remain inside this model are:
1. A viewer becoming an editor through a missing role check (none found — all mutations go through `authedWrite('editor')` or stricter).
2. An editor performing a destructive operation that should be admin-only (audited below — only DELETEs on operators / partners / initiatives / scenarios / contracts require admin; some others are editor-level which is intentional for tactical data).
3. Read leakage of another user's *personal* data — only notifications and advisor conversations are personal, and both filter on the actor.

## 4. Findings that deserve a follow-up (not "broken" but worth fixing)

### 4.1 `/api/admin/hearst/advisor` GET — read of any conversation by id (cross-user read leak)

```js
// app/api/admin/hearst/advisor/route.js  (~ line 393)
if (conversation_id) {
  const { data, error } = await auth.supa
    .from('hearst_advisor_conversations')
    .select('*')
    .eq('id', conversation_id)
    .single();
  ...
}
```

The list endpoint (just below) **does** scope by `actor_id`, but the single-conversation fetch does **not**. Any authenticated `editor` can read another editor's private LLM chat history simply by guessing/learning a conversation UUID.

**Fix — add a check at the start of that branch:**
```js
import { requireRowOwnership } from '@/lib/auth-guards';
// ...
if (conversation_id) {
  try {
    await requireRowOwnership({
      table: 'hearst_advisor_conversations',
      id: conversation_id,
      actorId: auth.actor,
      ownerColumn: 'actor_id',
      adminProfile: auth.profile,
    });
  } catch (err) {
    if (err instanceof Response) return err;
    throw err;
  }
  // …existing fetch…
}
```

This is the **single highest-impact finding** in the audit. Severity: medium — it leaks free-text strategic-advisor conversations, not credentials.

### 4.2 `/api/admin/documents` DELETE — editor deletes anyone's file and removes storage object

The `documents` table has an `actor_id` column (stamped on insert). The DELETE handler currently:
```js
const { data: doc } = await supa.from('documents').select('*').eq('id', id).single();
if (doc?.storage_path) await supa.storage.from(BUCKET).remove([doc.storage_path]);
const { error } = await supa.from('documents').delete().eq('id', id);
```

There is no actor check, and the storage object is destroyed irreversibly. Under the shared-workspace model this is "by design", but the actor_id column makes a "deleter must be uploader OR admin" rule trivially enforceable.

**Fix — between the lookup and the storage remove:**
```js
if (doc.actor_id !== auth.actor && auth.profile.role !== 'admin') {
  return NextResponse.json({ error: 'forbidden' }, { status: 403 });
}
```

### 4.3 `/api/admin/hearst/sources/[id]` DELETE — editor-level hard delete with no audit row

Hard deletion of evidence sources (`hearst_sources`) by any editor, no `hearst_audit_log` entry, no soft-delete. Sources are referenced by `_source_id` FKs on `hearst_scenarios`; orphaning is possible. Suggest either:
- Bump to `authedWrite('admin')` for DELETE, AND
- Insert a `hearst_audit_log` row with `action='delete_source'` before the delete.

Not an IDOR risk per se; flagged because the audit log is one of the table's stated purposes.

### 4.4 `/api/admin/stakeholders` DELETE — hard delete, no audit

Same shape as 4.3: editor-level hard delete by id with no actor / ownership / audit check. Shared-workspace, so not IDOR. Suggest soft archive or admin-only.

### 4.5 `/api/admin/team` POST — admin invites an existing user → silently re-grants role

If `inviteUserByEmail` fails because the email already exists, the route falls back to `update({ role, is_active: true, ... })` on the existing profile. This is admin-only and there's a last-admin guard on `team/[id]` PATCH, **but no equivalent guard here** — an admin could re-activate a disabled account or change another admin's role through this POST path with no extra confirmation. Tiny but worth a glance.

## 5. Schema gaps — tables that cannot be defended in code today

These tables have **no actor/owner column at all**, so even with `requireRowOwnership` you can only assert existence (`allowSharedWorkspace: true`). If a future multi-tenant pivot happens, these are the migrations to plan first:

- `crm.operators` — add `owner_profile_id uuid references crm.profiles(id)` or migrate `assignee_id` to gate access.
- `crm.partners` — same.
- `crm.initiatives` — `assigned_to` exists but is informational; if it becomes the access key, add a backstop trigger.
- `crm.tasks` — `assigned_to` same caveat.
- `crm.stakeholders` — no owner concept anywhere; would need full backfill from related operator/partner.
- `crm.workstreams` — seed table, shared by design.
- `crm.initiative_dependencies` / `_operators` / `_partners` — join tables, inherit parent ownership.
- `crm.hearst_data_room`, `crm.hearst_contracts`, `crm.hearst_pipeline`, `crm.hearst_sources`, `crm.hearst_scenarios`, `crm.hearst_projects` — all have `created_by` but no enforcement column distinct from it. `created_by` should be treated as "who first inserted" not as ACL.

If the app stays single-tenant, **no schema change is needed**: the routes are correct as-is. The only schema-level recommendation today is to enable a soft-delete pattern (an `archived boolean` column) on `crm.stakeholders` and `crm.hearst_sources` so DELETE handlers can stop being destructive.

## 6. Acknowledged limits of this audit

1. **No runtime probing.** I did not run the dev server, did not send crafted PATCH requests, did not test cookie / JWT replay. All findings are derived from static reading of `app/api/admin/**/route.js` + `middleware.js` + schemas. A live IDOR probe is the natural next step.
2. **No assumption about Supabase RLS at the database layer.** Every schema file in `scripts/` explicitly `disable row level security`. I did not query the live database to verify nothing was re-enabled out of band.
3. **`getAdminClient()` schema binding.** The helper uses `db: { schema: 'crm' }`, so `.from('public.foo')` would not work; the brief's snippet was tweaked accordingly in `lib/auth-guards.js`.
4. **Middleware coverage.** `middleware.js` matches `/admin/:path*` only — the API routes are reached as `/api/admin/...`, which **is not** matched by the middleware. Authentication for the API is therefore enforced *inside each route* via `requireProfile` / `authedWrite` (not by the middleware). This is fine — every mutating route does call one of those — but a future route added without that pattern would be silently unauthenticated. A defensive matcher addition (`'/api/admin/:path*'`) would be belt-and-braces; out of scope here.
5. **Dev autologin.** `getSessionProfile` honors `ADMIN_DEV_AUTOLOGIN_EMAIL` in dev. `middleware.js` does a fail-closed check that this env var is rejected on Vercel preview/production. This is correct, but worth keeping eyes on across env audits (agent A?).
6. **Storage bucket policies.** I did not inspect the Supabase Storage policies on `crm-documents`; document deletes go through service_role which bypasses them anyway. If anon ever gets `SELECT` on that bucket, signed-URL-only access would need to be re-verified.
7. **The advisor conversation read in §4.1** is the only true "row-level leak" I could find — and it is leak of read, not write.
